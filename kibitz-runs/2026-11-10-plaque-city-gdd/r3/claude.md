VERDICT: yes-with-fixes. No code exists yet (`src/` is not present in the repo — only `docs/GDD_AND_ARCHITECTURE.md` v0 and this input.md are committed), so nothing here is a "broken build"; but the spec itself contains several load-bearing contract contradictions that WILL cause cross-module wiring bugs if different modules are implemented against different readings of the same section.

MUST-FIX BEFORE BUILD:

1. [§6.4 vs §4 world_4] `BrushApplyParams.localPh: number` is a single scalar per `applyBrush()` call, but World 4's row in §4 describes `localPh` as a SPATIAL field (`4.2..7.4` mapped per-cell into `DataTexture.B`). A brush arc (`radius 1.6u`, `arc 95°`, §3.1) can span multiple cells with different pH in World 4, yet the contract only allows one pH value for the whole stroke. Fix: either (a) remove `localPh` from `BrushApplyParams` and have `applyBrush()` sample `OralChemistrySim`'s per-cell pH field directly for each touched cell, or (b) explicitly document `localPh` as "sampled once at probe center, applied uniformly across the arc" and accept the resulting edge-of-arc inaccuracy. This is exercised by Phase 1A's own `oralSurfaceGrid.test.ts` (§7.1, "per-cell critical pH shift"), so the ambiguity affects the first engine module built, not just later worlds.

2. [§6.6] Dual-write persistence (async IndexedDB `mouthlife_db`/`saves`/`primary` + sync `localStorage` `mouthlife_save_v2`) has no documented write-ordering or multi-tab/multi-device conflict policy. `MouthLifeSaveV2` carries no timestamp/version-vector field, and the ML2 Sync Code feature (§6.6) explicitly invites moving a save between devices/tabs. Two tabs open on the same browser, or an in-flight async IndexedDB write racing a later sync localStorage write for a DIFFERENT save event, can silently clobber newer data with older data. Fix: add a monotonic `lastWriteAt`/`writeSeq` to `MouthLifeSaveV2`, define last-write-wins reconciliation between the two stores on load, and/or use a `BroadcastChannel`/lock to serialize writes across tabs.

3. [§3 preamble vs §6.2 vs §6.4] Three different, mutually inconsistent claims about where the baseline constants (`CELL_SIZE`, `CLEAN_THRESHOLD`, `PROBE_RADIUS`, `CRITICAL_PH_HYDROXYAPATITE`, `CRITICAL_PH_FLUORAPATITE`, etc.) live: §3's preamble says "centralized in `src/config/gameConfig.ts`"; §6.2's directory tree agrees (`gameConfig.ts` = "Biophysical constants, radii, rates, quality caps"); but §6.4 prints the exact same consts under a section header naming `src/engine/types.ts`, and `types.ts` is independently described in §6.2 as types-only ("Vec2, Cartridge, Chemistry, Host, Save interfaces"). Every consumer module (`CollisionSystem`, `OralSurfaceGrid`, `ScoringEngine`, every test file in §7.1) needs one authoritative import path. Fix: pick `gameConfig.ts` (matches two of three references) and correct §6.4's header/placement; `types.ts` should only contain type/interface declarations, no runtime exported consts.

4. [§6.3.2 + §6.4 + §6.5] The `DataTexture`'s `B` channel is documented with FOUR different, world-dependent semantics (cervical margin density in W1; `gumIrritation` in W2; `localPh`/demineralization amber in W3-W4; EPS polymer maturity in W5), but `WorldCartridge` (§6.5's field list) has no field declaring which semantic is active. `OralSurfaceGrid`'s write path, the fragment shader's read path, `ScoringEngine`'s W2 tissue-preservation bonus (§5.1), and the §6.4 chemistry rule (`localPh` vs `criticalPh`) all independently need to agree on this per active world, with no shared source of truth. This breaks the stated "Engine Base First... Worlds mount as declarative WorldCartridge definitions" pillar (§1.1.1) for 4 of 5 worlds. Fix: add an explicit `WorldCartridge.bChannelMode: 'marginDensity' | 'gumIrritation' | 'localPh' | 'epsArmor'` (or equivalent) field that grid/shader/scoring all branch on, instead of each inferring world identity independently.

5. [§3.1 + §6.4 CellFlag.INTERDENTAL + §6.5 CollisionSystem] Two independent, undocumented-as-related enforcement mechanisms exist for the same invariant ("bristle cannot reach interproximal contacts < 1.20u"): a geometric block in `CollisionSystem` (AABB/circle vs `wallBoxes`/`interdentalAlleys`) and a cell-flag immunity in `OralSurfaceGrid.applyBrush()` (`CellFlag.INTERDENTAL` → "immune to applyBrush()"). Nothing states that the `InterdentalAlleyDef` AABBs and the grid region flagged `INTERDENTAL` must be generated from the SAME source data. If authored independently (hand-placed collision boxes vs hand-painted cell flags), the probe can visually enter an alley the collision system doesn't block while `applyBrush()` silently no-ops on those cells — a visible desync with no specified feedback cue. Fix: generate both from one cartridge-authored geometry definition (e.g., derive the `INTERDENTAL` cell mask directly from `interdentalAlleys[]` at cartridge-bake time in `WorldSession`/`CartridgeMeshBuilder`, not as two hand-authored datasets).

6. [§6.2 main.ts + §6.6 SaveSystem] No stated boot-order contract between registry population and save migration. `SaveSystem.migrateSave()` "validates IDs against `HostRegistry`/`UpgradeRegistry`" (§6.6), and `HostRegistry`/`UpgradeRegistry`/`CameoRegistry` module initialization order relative to `SaveSystem.load()` in `main.ts`'s bootstrap is never specified. If `SaveSystem.load()`/`migrateSave()` runs before these registries are fully populated (e.g., via a bundler code-split or lazy import), validation either throws or silently strips valid IDs. Separately, it's unspecified whether `UpgradeRegistry`/`HostRegistry` membership is phase-scoped (only Phase-1B's World-1 content registered) or always-fully-populated-but-gated — this matters because `migrateSave` must decide what to do with a synced save (`ML2:` code, §6.6) containing IDs from a later phase's content (e.g., `hydro_sonic_pulse`, a "World 2 Tier" upgrade per §3.2) loaded into a Phase-1B-only build. Fix: state the explicit bootstrap order (registries constructed → `SaveSystem.load()`/`migrateSave()` → cartridge registration → `SceneManager` init → `renderer.compile()` → first render) and define migration behavior for IDs unknown to the current build's registries (strip-and-continue, per the "lossless... clamps" language, should be made explicit for this case too).

7. [§6.2 EventBus.ts + §2.1 + §5.1] `EventBus` is described only as "Typed pub/sub with disposer functions" with zero enumerated event names or payload shapes, yet at least one event (Commensal Site reactivation) has three independent subscribers implied by the prose: `ScoringEngine` (+120 pts, §5.1), the visual "Ion Charge pulse" (implies `EntityBatchRenderer`, §2.1), and presumably `SoundEngine` for an SFX cue (§6.2's module list). Three systems built independently against the same unnamed event with no shared payload contract is a guaranteed integration failure point. Fix: add a minimal event table to §6.2 (event name, publisher, payload fields, subscriber list) for at minimum: commensal-site-reactivated, district-remin-wave-triggered, beacon-deployed, webgl-context-restored.

SHOULD-FIX:

1. [§6.3.3] `renderer.compile(scene, camera)` pre-warm is stated to happen "during bootstrap," but §6.3.2's `EnamelBiophysicsMaterial` uniforms (`uDiscloseOrigin`, `uDiscloseRadius`, `uDiscloseStrength`) and the `DataTexture` buffer must already be allocated with representative (even if zeroed) values at that point, or the first real Disclosing Scan (§3.1, item 4) can trigger a second, user-visible shader-permutation recompile — defeating the "hitch-free" §6.3.3 guarantee. State explicitly that ALL materials/uniforms/textures ever used in Phase 1B must exist before `renderer.compile()` is called.

2. [§6.3.3 QualityGovernor + EntityBatchRenderer] Tiers differ in particle count (60/180/400), and "switching tiers never recompiles shaders" is claimed, but it's never stated that `InstancedMesh` buffers are allocated at fixed `ultra` (400) capacity and only `mesh.count`/emission-rate is varied by tier. If buffers are instead sized per-tier, an auto upgrade mid-session (hysteresis `>57 FPS` up, §6.3.3) requires a buffer reallocation the doc never acknowledges. Fix: state explicitly that `EntityBatchRenderer` always allocates at ultra capacity; `QualityGovernor` only adjusts counts.

3. [§6.3.3 webglcontextrestored] The restore handler marks `dataTexture`/`InstancedMesh.instanceMatrix` buffers `needsUpdate = true` but never states whether the same pre-warm `renderer.compile()` step (bullet 2 of §6.3.3) must re-run after a context restore to preserve the "hitch-free" guarantee on the next render, since all GPU program objects are destroyed on context loss. [ASSUMPTION: Three.js's WebGLRenderer re-creates programs lazily on the next render call regardless; if so, the first frame after restore would still hitch unless compile() is re-invoked — verify against the actual Three.js version pinned in §6.1.]

4. [§6.2 ClockController.ts] One module is stated to own both the 60Hz fixed-dt sim clock and the "unskippable" real-time Brush-Along pacer clock, but these need different disciplines: the sim clock should clamp/skip catch-up frames on `visibilitychange` (to avoid a huge dt corrupting density sim on tab-return), while the pacer must either keep counting true wall-time while backgrounded (to remain genuinely "unskippable") or explicitly pause/resume with a visible paused state — the doc states neither, and conflating the two clocks risks either sim corruption or a trivially bypassable pacer (background the tab for 2 minutes).

5. [§6.6 + §2.2.2] `pendingSupplyBeacons` (counter, §6.6) is produced during Brush-Along and consumed as physical beacon placements in the NEXT Arcade run (§2.2.2), but the decrement point is unspecified. If decremented on Arcade world-load (eagerly) rather than on verified per-beacon pickup, a player who quits the Arcade run early loses the reward with no stated recovery — in tension with the Zero-Punishment Invariant (§1.1.4) even though this field is not itself a punished counter. Fix: decrement only on confirmed in-session pickup, with a save checkpoint at that point.

6. [§6.2 main.ts + §6.6 + §6.3.3] `qualityPreference` is persisted (`MouthLifeSaveV2`, §6.6) but §6.3.3's auto-detection (DPR/pointer-type/FPS hysteresis) and the save-load path's precedence over it is never sequenced. Given `SaveSystem`'s IndexedDB path is async while its localStorage mirror is sync, state explicitly that the FIRST-FRAME quality-tier decision is read from the synchronous localStorage mirror only (not blocked on the async IndexedDB open), with any later disagreement from IndexedDB reconciled in the background without a visible tier flicker.

7. [§6.3.3] Quality-tier thresholds (`DPR <= 0.9`, `60/180/400` particles, `<42`/`>57` FPS hysteresis, `5.0s` cooldown) are stated in prose with no citation to `gameConfig.ts`, even though §6.2 describes that file as covering "quality caps." Make explicit that these are `gameConfig.ts`-sourced constants like the biophysics constants in §6.4, for the same testability/tunability reasons.

8. [§6.3.2 + §6.5] The `DataTexture` is stated as a fixed `256x128 RGBA8` buffer, derived exactly from World 1's explicit `64u x 32u` dimensions (§4) at `CELL_SIZE = 0.25` (`64/0.25=256`, `32/0.25=128`). No other world in §4 states numeric `worldWidth`/`worldDepth`. Clarify whether texture resolution is a fixed engine constant (requiring all future `WorldCartridge.worldWidth/worldDepth` values to be normalized to bucket into 256x128) or computed per-cartridge as `worldWidth/CELL_SIZE x worldDepth/CELL_SIZE` (in which case §6.3.2's "256x128" is World-1-specific and should be stated as derived, not fixed, to avoid a texture-resize-on-world-load hitch that would violate the "zero scene reallocation" dive-transition promise in §6.3.1).

CUT THESE (over-engineering):
1. [§6.6] Dual-write IndexedDB + localStorage as two PRIMARY stores (not cache+primary) for Phase 1A/1B. `MouthLifeSaveV2` (§6.6) is a small JSON blob, well inside localStorage's ~5MB quota; running IndexedDB as a second primary store from day one adds the write-ordering/multi-tab race surface (MUST-FIX #2) for no benefit until the save payload or cross-device sync actually needs it. Safe to cut IndexedDB from Phase 1B and keep only localStorage + in-memory fallback; reintroduce IndexedDB later alongside the versioned conflict-resolution field it would need anyway.
2. [§3.3] `CameoRegistry`'s generalized multi-license (`ORIGINAL | CC0 | CC-BY-4.0 | MIT`) registry system, built for "optional verified open-source probe skins" that are not yet part of Phase 1B scope (only the single `DR-7 PERI` advisor ships). Safe to cut to a hardcoded advisor constant for Phase 1B and defer the generalized license-tagged registry until a second cameo/skin actually needs integrating — avoids building unused extensibility now.
