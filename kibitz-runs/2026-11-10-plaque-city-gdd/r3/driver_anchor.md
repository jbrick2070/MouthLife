ROUND 3 ANCHOR REVIEW (Driver: Antigravity UI)
Target: kibitz-runs/2026-11-10-plaque-city-gdd/r3/input.md

VERDICT: yes-with-fixes — Engine-first module boundaries and biophysical rules are solid, but R3 exposes four real integration/sequencing hazards: an IndexedDB-vs-localStorage stale-read race on tab close, buff consumption on aborted runs, Z-buffer precision / input-gating during the Powers-of-Ten orbital zoom, and unspecified EventBus topic/teardown contracts.

MUST-FIX BEFORE BUILD:
1. [§6.6] Async `IndexedDB` vs synchronous `localStorage` boot reconciliation race (CONFIRMED against r3/input.md): §6.6 says "On boot, reads IndexedDB first, falling back to localStorage if empty/unavailable." Because `localStorage` writes complete synchronously while `IndexedDB` transactions commit asynchronously, closing a browser tab immediately after completing a Brush-Along can leave `localStorage` at revision `N+1` while `IndexedDB` still holds revision `N`. Reading `IndexedDB` blindly first on next boot silently discards the user's latest stamp, violating Pillar 4. Fix: Add `saveRevision: number` (monotonic per write) to `MouthLifeSaveV2`. During async `SaveSystem.init()` (awaited in `main.ts` *before* mounting UI or entering `HUB`), read both stores, validate both via `migrateSave`, pick the payload with higher `saveRevision` (taking `Math.max` on `totalBrushStamps` if revisions tie), and write back to synchronize both stores.
2. [§6.3 item 1, §6.2] *Powers of Ten* orbital-to-micron zoom Z-fighting and mid-transition input race (CONFIRMED against r3/input.md): §6.3.1 describes zooming from a 3D Earth in space down to 100-micron tooth topography in one `SceneManager` without defining world coordinates, `camera.near`/`far` frustum bounds, or input gating during the `1.4s` dive. Spanning real planetary-to-micron ratios in one frustum destroys 24-bit depth buffer precision on mobile/integrated GPUs. Fix: Use a bounded theatrical scale inside a fixed frustum (`near = 0.5, far = 320`): place `OrbitalEarthBackdrop` (`earthGroup`, `radius = 18u`) centered at `(32, 110, 16)` above `archGroup` (`[0..64] x [0..4.5] x [0..32]`). Gate `InputManager` gameplay actions while `CameraRig.isTransitioning === true`, and swap `earthGroup.visible` <-> `archGroup.visible` at `t = 0.55` behind a brief HUD telemetry aperture flash.
3. [§2.2 item 4, §6.2 `WorldSession` <-> `SaveSystem`] Unspecified consumption lifecycle for `pendingSupplyBeacons` and `remineralizedOverdriveRuns` (CONFIRMED against r3/input.md): Neither §2.2.4 nor §6.6 specifies *when* `pendingSupplyBeacons` and `remineralizedOverdriveRuns` decrement. Decrementing at `WorldSession` start punishes accidental page refreshes or returning to Hub early. Fix: Read `pendingSupplyBeacons` and `remineralizedOverdriveRuns > 0` at `WorldSession` start to configure the session, but commit their consumption (`remineralizedOverdriveRuns = Math.max(0, prev - 1)`, `pendingSupplyBeacons = remainingUncollected`) inside `SaveSystem` **only on `MISSION_COMPLETE`**.
4. [§6.2 `EventBus.ts` & UI Overlays] Missing canonical `AppEventMap` contract and overlay teardown order (CONFIRMED against r3/input.md): Four UI overlays, `SoundEngine`, `WorldSession`, and `SaveSystem` communicate via `EventBus.ts`, yet zero event names/payloads or mount/unmount teardown lifecycles are specified. Fix: Define the typed `AppEventMap` and an `OverlayView` interface (`mount(root): void; dispose(): void`) in §6.4/§6.6, guaranteeing `main.ts` calls `activeOverlay.dispose()` (unsubscribing all `EventBus` disposers and DOM listeners) *before* mounting the next mode's overlay.
