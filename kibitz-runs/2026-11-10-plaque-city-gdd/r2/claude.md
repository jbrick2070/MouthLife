VERDICT: yes-with-fixes — the architecture is internally coherent and the stack is real, but several core sim contracts (tool-mutation function signatures, player collision radius, the margin-fissure bonus formula) are never specified concretely enough to write the named test files against, and two independently-authored data sources (alley geometry vs. grid flags) have no stated sync mechanism.

MUST-FIX BEFORE BUILD:
1. [§6.2/§6.3/§7] `PlaqueGrid.applyBrush()`, `applyFlossSegment()`, `applyMouthwash()` (and the Disclosing Pulse read-op) are referenced by name throughout §3.1, §6.3, and are the explicit subject of `plaqueGrid.test.ts`, but no signature is given anywhere — not parameters (world position? facing angle + arc? precomputed cell list?), not return type, not whether they take `dt` or apply instantaneously. These are the hottest, most-tested functions in the whole project and cannot be implemented or unit-tested from the document as written. Fix: add explicit signatures, e.g. `applyBrush(cx: number, cz: number, facingRad: number, arcRad: number, radius: number, dt: number): void`, `applyFlossSegment(x0,z0,x1,z1: number): AffectedCellsSummary`, `applyMouthwash(cx,cz,radius: number): void`.
2. [§4.1/§6.2/§6.3 item 1] Alley geometry ("Interdental Passages, width 0.9u") lives in `LevelLayout.ts`; the `INTERDENTAL`/`PAINTABLE`/`MARGIN_FISSURE` cell flags live independently in `PlaqueGrid.ts`. No generation pipeline is specified that derives one from the other, so a level author can create a 0.9u geometric corridor that isn't flagged `INTERDENTAL` (or vice versa), silently breaking the Toothbrush-immunity / Floss-only rule. Fix: state that `PlaqueGrid` flags are baked from `LevelLayout` geometry at load time (single source of truth), or vice versa, with a named function (e.g. `bakeFlagsFromLayout(layout): Uint8Array`).
3. [§3.1/§4.1/§6.2 Collision.ts] Whether Captain Bristle's own body can enter a sub-1.2u/0.9u corridor (vs. only the Floss "zip" bypassing it) depends on the player's collision-circle radius, which is never defined anywhere in the document or implied to live in `gameConfig.ts`. Without `PLAYER_RADIUS` and the explicit invariant `PLAYER_RADIUS > alleyWidth / 2` for sealed corridors, `Collision.ts`'s "alley width block" cannot be implemented or tested (`collision.test.ts` names this exact scenario). Fix: add `PLAYER_RADIUS` to §6.3's data contracts and state the blocking inequality.
4. [§3.3] "+45% on MARGIN_FISSURE cells... unless angled_bass_bristles is equipped" is ambiguous between two different formulas with very different gameplay outcomes: (a) the bonus modifies the existing 0.65x margin penalty → `0.65 × 1.45 ≈ 0.9425x` (margin cells approach but never beat normal-cell speed), or (b) the bonus modifies the full base rate → `0.95/s × 1.45 ≈ 1.3775/s` (margin cells become faster to clean than open plaza, which reads as backwards). `plaqueGrid.test.ts` names this exact bonus as a required assertion and cannot be written without resolving it. Fix: state the formula explicitly, e.g. `effectiveRate = baseRate * (equipped ? 0.65 * 1.45 : 0.65)`.
5. [§3.1/§4.1] Floss Pick "zips Captain Bristle through open interdental shortcuts if fired down an alley channel" introduces a discrete movement mechanic (dash/teleport) with zero defined kinematics: duration, speed/velocity curve, whether normal collision is suppressed mid-zip, and what happens if the filament's far end is itself blocked. This is a distinct feature from the density-mutation `applyFlossSegment()` and needs its own contract before `ArcadeSim.ts`/`Collision.ts` can implement it.
6. [§6.3 item 1] "GPU Texture Sync... B = districtSealState" has no backing data source. The documented Cell Arrays are `density`, `flags`, and `districtId` — there is no per-cell or per-district "sealed" boolean anywhere to derive this byte from. Fix: add a `sealedDistricts: boolean[4]` (or equivalent) to the data contracts and state `B = sealedDistricts[districtId[idx]] ? 255 : 0` (or similar).
7. [§6.1] `noUncheckedIndexedAccess: true` makes every `density[idx]`, `flags[idx]`, `districtId[idx]` TypedArray read resolve to `number | undefined` under TypeScript's type system (TypedArrays carry a numeric index signature, so this flag applies to them exactly as to plain arrays). This touches the single hottest code path in the project (`PlaqueGrid.ts`, `Collision.ts`, the per-frame texture sync) and the document gives no access-safety convention (wrapper accessor, non-null assertion, or disabling the flag for sim files). This will force either a rewrite pass or constant friction at the keyboard if decided after the fact. Fix: pick and state the convention before writing `PlaqueGrid.ts`.
8. [§6.1] Auto quality-tier switching triggers on a bare "rolling 90-frame FPS < 45" with no hysteresis or debounce. A system oscillating around the 44–46fps boundary will flip `balanced ↔ high` repeatedly; each flip changes shadow technique (directional shadow map ↔ "blob contact shadows"), which is a scene-topology change (adding/removing shadow-casting, likely forcing shader/program rebuilds under the `onBeforeCompile`-injected material), i.e. the "fix" for low FPS can itself cause stutter. Fix: add separate up/down thresholds (e.g. downgrade <40fps, upgrade >55fps) and a cooldown window before the next re-evaluation.
9. [§6.3 item 4] `navigator.wakeLock?.request('screen')` wrapped "inside try/catch" does not protect against the real failure mode: `.request()` returns a Promise that can reject asynchronously (e.g. `NotAllowedError` when the document isn't visible, which is common right when the Brush-Along screen is opening). A synchronous try/catch around the call will not catch that rejection, producing an unhandled promise rejection at runtime. Fix: `navigator.wakeLock?.request('screen').catch(() => {})`.

SHOULD-FIX:
1. [§6.3 item 1] The "dirty bounding box" partial-texture-update claim does not match plain Three.js behavior: setting `dataTexture.needsUpdate = true` triggers a full `texImage2D`/`texSubImage2D` upload of the *entire* image regardless of any bbox tracked in JS. Three.js does have a real partial-upload mechanism (`texture.updateRanges`), but it is not named here. At 256×128×4 = 128KB total, a full upload every frame is already cheap — either drop the bbox bookkeeping (see CUT #1) or explicitly adopt `updateRanges` if partial upload is actually wanted.
2. [§6.2/§6.3] No shared source of truth is named for `terrainHeight(x,z)`. If `PlaqueCityMesh.ts` (vertex generation) and whatever positions the player/citizens/beacons on Y each implement their own height calculation, they will drift and produce visible floating/clipping. Fix: name one pure function (e.g. exported from `LevelLayout.ts`) used by both.
3. [§6.2] Entity spawn-position data (Citizens, Sugar Shards, Biofilm Bridges, Saliva Fountains, Beacon drop points) has no stated home. `LevelLayout.ts`'s documented scope is "district geometry bounds, walls, alleys" only — entity placement needs its own table/module or an explicit extension of `LevelLayout.ts`'s responsibility.
4. [§6.3 item 2] `webglcontextrestored` handling is stated as "rebuild `dataTexture.needsUpdate = true`," but a lost context invalidates *all* GPU resources — compiled shader programs, InstancedMesh attribute buffers, and any other textures. The recovery plan should enumerate everything that needs re-flagging/rebuilding, not just the one texture mentioned.
5. [§2.2.4] No cap is stated on repeated same-day "+5 Crystal courtesy tip" Brush-Along runs beyond the 2x full-reward cap. If the 120s pacer can be skipped/fast-forwarded, this is an unbounded currency-farming exploit; if it cannot be skipped, the exploit is naturally rate-limited to real-time replays. State explicitly that the pacer cannot be skipped, or add a daily courtesy-tip ceiling.
6. [§6.3 item 3] "`ML1:<base64url(JSON)>`" names an encoding with no stated implementation path. `btoa`/`atob` in browsers produce standard base64 (`+ / =`), not base64url — producing base64url requires manual alphabet substitution (or the newer, not-universally-available `Uint8Array.prototype.toBase64()`). State the exact encode/decode function to use.
7. [§2.2.4/§6.3 item 3] `remineralizedOverdriveRuns` accumulation on a second same-day claim while a previous Overdrive buff is still active is unspecified — reset to 2, or add up to some cap? State the rule.
8. [§3.1] The Floss Pick's mouse-aim raycast target plane is unspecified. Terrain height varies 0–4.5u and the camera is a 55°-pitched perspective (not orthographic top-down), so a flat y=0 raycast plane will visibly misalign the cyan aim preview from the player's actual on-screen cursor position whenever standing on a raised cusp/ridge. State whether aiming raycasts against the terrain mesh or a plane tracking the player's current terrain height.
9. [§6.1] "< 35 draw calls" doesn't state whether the ceiling includes the shadow-map depth pass. `renderer.info.render.calls` (the natural verification metric for this budget) counts both the color pass and any shadow-casting depth pass, so the real number in `high` tier could run close to 2x the stated figure for shadow-casting instanced batches.
10. [§2.1/§6.3] District-cleanliness/seal-check computation strategy (brute-force per-frame scan of 32768 cells vs. incremental per-district clean-cell counters updated at tool-application time) is unstated. Not a hard performance ceiling at this grid size, but the two approaches are different enough in code shape that the ambiguity should be resolved before `ArcadeSim.ts` is written.

OPTIONAL / NICE-TO-HAVE:
- [§4.2] Name the easing curve for the "0.25s elastic knockback" (e.g. a specific ease-out so it's deterministic for `arcadeSim.test.ts` if ever extended to cover it).
- [§6.1] Revisit whether `three@^0.174.0` is still the intended pin (it is a real, valid Three.js version string) or should be bumped, given how much time has likely passed since it was chosen.
- [§6.3 item 1] If more than one variant of the `onBeforeCompile`-injected GLSL ever exists across materials, set `material.customProgramCacheKey()` to avoid Three.js's shader-program cache serving a stale compiled variant; not needed today with a single shared material.

CUT THESE (over-engineering):
1. [§6.3 item 1] Dirty-bounding-box tracking for the plaque `DataTexture` update. The full buffer is 256×128×4 = 128KB; uploading it whole every frame is already trivially cheap on any target device, and (per SHOULD-FIX #1) the stated mechanism (`needsUpdate = true`) doesn't actually achieve a partial upload anyway. The bbox bookkeeping adds code and edge cases (stale bbox after a seal cascade touches cells outside the last-tracked region) for no measurable win.
2. [§6.1] The separate "blob contact shadows" technique for `balanced` tier. Building, testing, and runtime-switching between two distinct shadow-rendering code paths is real engineering cost for a solo-dev Phase-1 vertical slice, and is also the direct mechanism behind MUST-FIX #8's stutter-loop risk. Simply disabling shadow-casting entirely on `balanced` tier removes a whole render path and its edge cases at the cost of a flatter look on low-end devices — an acceptable Phase-1 trade.

[ASSUMPTION] Three.js `^0.174.0` is assumed to render exclusively via WebGL2 (recent Three.js releases dropped the legacy WebGL1 renderer), which is why GLSL ES 3.00 bitwise flag-unpacking (`flags & 0x08`) in the custom `onBeforeCompile` shader is assumed safe on "modern mobile browsers" per §1.1 pillar 4 — verify against the actual installed `three` version before relying on bitwise ops in the injected fragment shader.
